# Phase 1 baseline — 2026-08-21

First recorded run of `bench_engines`, establishing the scalar starting point.

## Machine

| | |
|---|---|
| CPU | Intel Core i5-8400H @ 2.50 GHz (Coffee Lake, 4C/8T) |
| ISA | SSE4.2, AVX, AVX2 — **no AVX-512** |
| Cache | L1d 32 KiB ×4, L2 256 KiB ×4, L3 8 MiB |
| OS | Linux 6.18 (WSL2) |
| Compiler | GCC 15.2.0, `-O3` |
| vphilox | 2026.08.0, backend `scalar` (SIMD kernels not implemented) |

Caveats: WSL2, no frequency pinning, shared machine. Treat these as
order-of-magnitude, not publication figures. Phase 4 needs a quiet, pinned
box.

## Results

Working set is 256 KiB per iteration — fits L2, so this measures the generator
rather than memory bandwidth.

| Benchmark | Throughput | Notes |
|---|---|---|
| `BM_vphilox` | 954 MiB/s | through the engine's refill buffer |
| `BM_vphilox_bulk` | 1.231 GiB/s | raw kernel, no buffering |
| `BM_mt19937` | 1.261 GiB/s | the baseline to beat |
| `BM_philox_scalar` | 1.208 GiB/s | scalar kernel, forced |

## Finding: the 10× scalar penalty does not reproduce here

The project's framing (`docs/Research on vPhilox.md`, `docs/Vector Philox
Development Strategy.md`) rests on NVIDIA's XGBoost observation that scalar
Philox runs ~10× slower than `std::mt19937`. On this machine it runs at
**0.96× of mt19937** — essentially par.

A follow-up isolating the effect:

| Case | Throughput |
|---|---|
| One block at a time, carried dependency between iterations | 1.13 GB/s |
| Independent counters, batched loop | 1.31 GB/s (1.16×) |

So cross-block instruction-level parallelism is worth ~16% in scalar code, not
10×. GCC 15 at `-O3` schedules the wide multiply well enough that the
dependency chain is not the disaster the citation describes.

Possible explanations, none yet verified:

- The XGBoost measurement may have gone through a heavier abstraction layer
  (a `std::` engine wrapper, per-call virtual dispatch, or re-seeding per draw)
  rather than a tight Philox loop.
- It may have used Philox4x**64**, whose 64×64→128 multiply is far more
  expensive on x86 than the 32×32→64 used here.
- It may predate compilers that schedule this pattern well.
- Coffee Lake's multiplier may simply be better-suited than whatever part was
  measured.

**This does not invalidate the project**, but it does change the pitch. The
honest claim is not "recover a 10× regression" — it is "counter-based
generation gives you O(1) seeking, lock-free parallelism, and cross-platform
bit parity, and SIMD makes it *faster* than mt19937 rather than merely equal."
A 4–8× SIMD speedup over this 1.2 GB/s baseline lands at 5–10 GB/s, which is a
strong result on its own terms.

**Action:** re-measure on a machine with AVX-512 and on ARM before committing
the framing to the paper. If the 10× figure cannot be reproduced anywhere, the
paper should cite it as reported context rather than as a result, and lead with
the properties instead. Tracked in `ROADMAP.md` Phase 1.

## Finding: the refill buffer costs ~22%

`BM_vphilox` (954 MiB/s) vs `BM_vphilox_bulk` (1.231 GiB/s) — the engine's
per-call path gives up about a fifth of the raw kernel throughput to buffer
bookkeeping.

That gap is the thing Phase 3's "zero-cost abstraction" claim has to close, and
right now it is not close. Worth profiling: the bounds check per `operator()`
is the obvious suspect, and a bulk `generate_n`-style API would let callers who
do not need one-value-at-a-time skip it entirely.

## Reproducing

```bash
cmake --preset bench
cmake --build --preset bench
./build/bench/benchmarks/bench_engines --benchmark_min_time=0.5s
```
